# Languages

Four locales ship: English, Spanish, Arabic, Amharic. This is what that means
in practice and what is still owed.

## Read this first

**The Spanish, Arabic and Amharic copy has not been reviewed by a native
speaker.** It was written to be idiomatic rather than translated line by line,
and the choices behind it are documented at the top of each file, but it is
one writer's work and it needs a second pair of eyes per language before it
goes in front of parents. That review is the last thing between here and
launch, not a nice-to-have: copy that is merely correct reads like a form, and
the whole argument of this product is that it does not sound like one.

## Two languages, not one

A parent's language and their child's school language are different questions
and the product asks both.

- `Parent.language` is who we are talking to. The primer, the questions, the
  scripts, every word of the interface.
- `Child.schoolLanguage` is the language of the worksheet and the classroom.
  Null means it is the same as the parent's, which is the ordinary case.

Where they differ, a key mathematical term is written in the parent's language
with the school's term in parentheses, once:

> El número de abajo se llama denominador (denominator).

A mother reading Spanish whose daughter is taught in English needs to
understand the idea *and* recognise the word her daughter will hear on Monday.
One of the two alone fails her.

The rule lives in `prompts/generate-packet.md` and `prompts/chat-turn.md`.
A transcription is never translated: what was printed on the page stays as it
was printed.

## The catalogue

`lib/i18n/messages/en.ts` is canonical. Every other locale is an overlay that
carries only what it translates and inherits the rest, so a string added in
English is visibly English elsewhere rather than silently missing.

Launch coverage is the product surface, about 66% of the catalogue. The
marketing pages under `app/(site)` stay English by decision: they are
argument-shaped prose where a weak translation costs more credibility than it
buys. `/ops` and the studio panel are English because they are for the team.

`npm run check` asserts the coverage floor per locale, so a catalogue cannot
rot quietly back towards English.

### Adding a locale

1. Add a row to `LOCALES` in `lib/i18n/locales.ts`: direction, script, number
   profile, and `translated: false` until the catalogue exists.
2. Write `lib/i18n/messages/<code>.ts` as a `LocaleOverlay`. Do not translate
   the English. Write what a parent in that language would find plain.
3. Register it in `OVERLAYS` in `lib/i18n/index.ts` and set `translated: true`.
4. If it is right to left, add the code to the inline script in
   `app/layout.tsx`. The check suite asserts the two lists agree.
5. If it needs a script the font stacks do not cover, add a Noto face to both
   `app/globals.css` and the Google Fonts link in `app/layout.tsx`.

## Numbers

`lib/i18n/numbers.ts`, driven by the profile in the registry. It states the
decimal separator, the thousands separator, the division and multiplication
signs, the percent sign and the digit set, because `Intl.NumberFormat` will
not commit to the last three and those are the ones a textbook fixes.

| locale | 1234.5 | digits | notes |
|---|---|---|---|
| en | `1,234.5` | Latin | |
| es | `1.234,5` | Latin | Peninsular. Mexico is the other way round and wants an `es-MX` row. |
| ar | `١٬٢٣٤٫٥` | Arabic-Indic | U+066B decimal, U+066C thousands, U+066A percent. Mashriq and Gulf convention; the Maghreb uses Western digits. |
| am | `1,234.5` | Latin | Ethiopic numerals exist and are not used for arithmetic. |

**Numbers the product generates go through this. Transcriptions never do.**
Re-notating a child's working would show a parent something their child did
not write.

## Right to left

- `dir` is set on `<html>` by an inline script in `app/layout.tsx`, mirroring
  how the theme is applied, so the prerendered marketing pages stay static.
  `LocaleProvider` keeps it in step on navigation.
- The stylesheet uses logical properties throughout. `npm run check` fails on
  a physical one outside a `[dir=...]` rule.
- Directional chevrons take `direction="start"` or `"end"` and are flipped in
  CSS, so `components/icons.tsx` stays a server component.
- The logo lockup keeps its order: "ParentPilot" is a Latin proper noun in
  every locale and a mark that jumped sides would read as a different logo.
- Handwriting and worksheet scans are never mirrored.

### The bug worth knowing about

`1/4 + 2/3 =` inside an Arabic card renders as `= 2/3 + 1/4`. The bidi
algorithm reorders a run of neutral characters by the direction of the
paragraph around it, and the result is not a cosmetic flaw: it is a different
problem from the one the child is looking at, shown under a heading that says
this is what we read off their page.

Anything quoted from the page carries `.pp-transcript`; anything the product
generated as an expression carries `.pp-expression`. Both are
`unicode-bidi: isolate`. Model prose carries `unicode-bidi: plaintext`, which
takes each paragraph's direction from its own first strong character, so a
bilingual key term keeps its parenthesis attached to the word it belongs to.

`npm run check` asserts the class is present at every render site that prints
a transcription.

## Curriculum

`Standard.curriculum` is `CCSS`, `ENC` (England National Curriculum) or
`CBSE`, and retrieval is scoped to the child's. A parent in Delhi being told
what the Common Core expects is worse than being told nothing.

When a child's curriculum holds no match, the search falls back to the whole
corpus and the packet carries a notice naming both curricula. Useful from
somebody else's syllabus is worth having; useful from somebody else's syllabus
that looks like your own is not.

Only Common Core is seeded. `seed/standards-england.json` and
`seed/standards-cbse.json` are empty templates. See `seed/README.md`, which
also says why nothing in them is model written.

## Misconceptions stay English

`seed/misconceptions.json` is canonical data: one description per
misconception, shared by every locale, rendered into the parent's language at
generation time by the prompt. Translating the file would fork the description
that a match is judged against, and twenty descriptions across four languages
would drift.

`npm run check` fails if a non-Latin character appears in that file.

## What the eval covers

`npm run eval -- --only=locales` runs retrieval and packet generation in each
launch locale and asserts four things per locale: that the localised probes
still land on the right standard, that the packet is written in that locale's
script, that the computed answer is still absent from the prose, and that the
canonical English misconception is not quoted at the parent.

The script assertion catches the commonest multilingual failure, a model that
agrees to write Arabic and answers in English. **It cannot catch that for
Spanish**, which shares a script with English. That hole closes when a person
reads one Spanish packet, which is the review this document opens by asking
for.

## What is still owed

1. **Native review of all three locales.** Blocking for launch.
2. **The England and CBSE corpora.** Retrieval falls back and says so until
   they land, which is honest but is not the product.
3. **An `es-MX` overlay.** Mexican number notation is the reverse of Spain's
   and the vocabulary differs; today a Mexican family gets Peninsular Spanish.
4. **The marketing pages**, if the launch wants a parent to arrive at the
   front door in their own language rather than at `/app`.
5. **Plural forms.** Arabic has a dual and more than one plural; Amharic
   marks plurality differently again. Nothing in the catalogue needs a count
   inside a sentence yet. The first string that does will need real plural
   rules rather than a helper that pretends.
